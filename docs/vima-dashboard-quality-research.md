VIMA dashboard quality: research and proposed platform changes

Research date: 20 October 2026. This is a proposal, not a claim that the full workflow below has been implemented. The product goal is that users work with VIMA directly; developers improve its capabilities and acceptance criteria rather than manually authoring each client's dashboard.

The main recommendation is to give VIMA an executable design specification, data preparation tools, a renderer capable of honoring that specification, and a browser-based review/repair stage. Better model instructions help, but cannot compensate for a missing renderer or absent verification tools.

Publicly documented approaches:

| Product | Documented mechanism | Relevant lesson for VIMA |

| Claude | Anthropic describes an experimental generator/evaluator architecture: a separate evaluator navigates the application with Playwright, grades explicit criteria and returns actionable feedback. It also reports evaluator leniency and iteration costs. | Evaluate the actual dashboard against the user's requirements and reference, with a calibrated reviewer and bounded repair budget. This is a published engineering experiment, not proof that every Claude interaction uses this architecture. |
| Base44 | Its documentation describes global theme controls, element editing, previews and reverting changes. Its Design Pack describes visual references and edits scoped to a selected section. | Store design intent persistently, make edits local, and keep reversible versions instead of restyling the whole dashboard for each request. Public documentation does not establish its private model prompts or orchestration. |
| OpenAI / ChatGPT | Official frontend guidance recommends design constraints, visual references and Playwright verification. Separate agent documentation recommends traces and repeatable evaluations. | Give VIMA visual input and tools to inspect its output; measure the resulting workflow. These are documented capabilities and engineering guidance, not a reconstruction of ChatGPT's private system prompts. |

Current VIMA observations from the code, before the parallel template work is completed:

- `plan_dashboard` identifies schema candidates and returns general planning instructions. It does not establish an executable acceptance specification or prove completeness of the requested analysis.
- `review_dashboard_design(publication_id=...)` explicitly reviews saved configuration and chart definitions. It does not observe browser appearance or prove numerical accuracy.
- The custom renderer supports particular chart families and falls back to tables for unsupported visualizations. Chart availability in Superset does not establish renderer compatibility in VIMA.
- The generic layout uses saved card dimensions and can produce a scrolling page. The Buikwe workspace has different, compact layout behavior. Shared interaction and layout primitives should span templates.
- Administrative enrichment already contains name matching and point-in-polygon logic. It needs discoverable preparation tools and useful diagnostics so VIMA can select and validate joins independently.
- The agent accepts a model end-of-turn without a dashboard completion gate (`agent/loop.py`, approximately line 1214). Configuration review is requested in prompts but is not evidence-backed lifecycle enforcement.
- Tool results are currently serialized as JSON text (`tools/registry.py`, approximately line 270). A screenshot tool must return actual multimodal image blocks to model vision; a base64 string inside JSON is insufficient. Existing uploaded image/PDF handling in `attachments.py` already provides a useful integration pattern.
- The renderer infers dimensions and numeric measures and maps rows directly (`frontend/app.tsx`, approximately line 213). Explicit multi-series encodings, pivots, time scales and formatting belong in the renderer contract, rather than expecting the model to overcome these limits through prose.

Recommended work, ordered by dependency:

1. Persist the design and analytical brief. Store audience, questions, requested template/version, original reference, required measures, interaction behavior, target viewports and explicit preservation instructions. For a supplied design, VIMA must bind data into that design. For a new design, VIMA may compose within the platform's supported layout and interaction system. A request to recolor one chart must not implicitly authorize a layout change.

2. Make the rendering contract explicit. A template registry needs its original artifact, runtime dependencies, supported chart hosts, binding schema, theme tokens and compatibility status. Preserving an HTML file is useful but does not make its custom runtime available. Do not silently substitute an approximate renderer. Expose capabilities before VIMA chooses chart types, so an unsupported map is not published as an accidental table. Keep exact supplied templates separate from the general composition engine.

3. Share interaction primitives. Chart stacks, selectors, legends, popup configuration, cross-filtering, detail drawers and reset behavior should be reusable across templates. A stack is one spatial panel with multiple related charts, not several cards appended vertically. Persist active state where useful; update data when filters change; make its tabs work with a keyboard. Use saved client chart references, not benchmark IDs.

4. Plan the analysis before arranging charts. VIMA should determine source grain, unique entities, duplicate risks, date coverage, denominators, missingness, refresh time and the evidence for each requested measure. Define the questions each view answers and which details are available through tabs or drilldowns. Record absent data honestly. Cluster statistics and alert labels require an actual method, not an attractive placeholder.

5. Expose geographic preparation as a tool workflow. Inspect the permitted source, discover exact-region reference layers, choose normalized administrative-name matching or spatial containment, validate cardinality and coverage, and pass the resulting configuration to the publisher. Return counts for matched, unmatched, ambiguous and conflicting records, the geographic basis and source provenance. Name joins should yield named areas or polygons; derived centroids need explicit labels. Joining must preserve saved source filters and viewer permissions.

6. Validate the dashboard in a draft browser session. Exercise the real publication with an authorized viewer session. Collect screenshots, bounding boxes, chart errors and query outcomes for each tab at the agreed viewports. Return screenshots to model vision as image content, not encoded text. Check that chart labels, selectors and legends remain readable. Enforce viewport fit through panel allocation, stacks and detail surfaces; hiding overflow or scaling every label down is insufficient. Test long names, empty selections, missing values, slow data, multiple filters, reset and marker popups.

7. Add a separate visual evaluator and bounded repair. Give it the original reference, current screenshots, acceptance specification and deterministic checks. Grade fidelity, information hierarchy, typography, density, detail and interactions. Its findings must identify a target and a supported repair action. For an exact supplied design, reward fidelity, not novelty. Preserve the best validated candidate and stop after a small configurable repair budget; do not copy a long research loop into every user interaction. For small style edits, inspect only affected targets plus required regression checks.

8. Make completion evidence-based. Draft creation and publication should be distinct lifecycle steps. The system should track whether queries, bindings, interactions and target viewports were checked. Publish automatically within existing user authorization when the requirements pass. If they do not pass, keep the working version and report the specific unfinished requirement. A successful build or a configuration verdict is insufficient evidence of visual quality.

9. Build a benchmark from real VIMA tasks. Include exact SINCEP reference reproduction, a different template with stacked charts, a new dataset without coordinates but with administrative names, spatial joins with ambiguous locations, a targeted color edit, and a dense dashboard at common laptop widths. Score data correctness, required content, reference fidelity, readability, working interactions, join quality and preservation of unrelated settings separately. Run end-to-end VIMA conversations, not only helper unit tests. Use these results to compare prompts, tool surfaces and models before making model routing or training decisions.

Suggested first delivery is the design contract, shared stacking, renderer compatibility checks and browser review for draft publications. Follow with analytical/geographic planning and the independent repair evaluator. Maintain a small benchmark throughout. Success means VIMA repeatedly produces a complete, readable dashboard from a user's request without a developer manually choosing its charts or fixing its layout.
